## Context

当前仓库仅包含 OpenSpec/OpenCode 元数据，没有可运行的前后端代码。目标是在最短路径内建立一个可维护的全栈 TypeScript 工程，验证 OpenCode Session 读取与状态展示链路。约束条件包括：

- 前端必须使用 React，构建工具使用 Vite，并启用 SCSS。
- 服务端必须使用 Node.js + Koa，对 OpenCode API 做后端聚合，不在浏览器端直连 OpenCode。
- 初始版本仅需展示最新 10 个 Session，不引入游戏引擎，视觉风格通过 CSS/SCSS 实现。
- 工程质量基线必须包含 ESLint 与 Prettier，保证后续迭代一致性。

## Goals / Non-Goals

**Goals:**

- 建立前后端分层明确的工程结构，支持本地联调和生产构建。
- 提供稳定的后端 Session 聚合接口，统一输出列表与状态。
- 提供前端首页默认展示最新 10 个 Session，并体现偏游戏向但轻量的 UI 风格。
- 形成可执行的脚本体系（dev/build/lint/format），作为后续功能扩展基线。

**Non-Goals:**

- 不实现复杂会话详情、会话编辑、分享或历史回放。
- 不引入游戏引擎、物理系统或复杂渲染框架。
- 不在初始阶段加入完整鉴权体系或多租户能力。
- 不覆盖 OpenCode 全量 API，只聚焦会话概览所需最小子集。

## Decisions

### 1) 采用 workspace 结构隔离前后端

- 决策：使用 `apps/web`（React+Vite）和 `apps/server`（Koa）结构。
- 原因：前后端关注点分离，后续可独立演进；同时保留单仓协同与统一脚本。
- 备选方案：单包混合前后端。未采用原因：构建与运行边界不清晰，类型和依赖管理易耦合。

### 2) OpenCode 接入走服务端网关层

- 决策：Koa 服务器调用 OpenCode SDK/API，前端只调用本地后端 `/api`。
- 原因：避免前端暴露 OpenCode 连接参数与潜在认证信息，统一错误处理与数据整形。
- 备选方案：前端直连 OpenCode。未采用原因：CORS、认证与兼容性复杂度更高。

### 3) 会话列表与状态在后端聚合后返回

- 决策：后端先获取 `session.list(limit=10)`，再结合 `session.status` 组装响应。
- 原因：前端渲染简单，避免多次请求和状态映射分散在 UI 层。
- 备选方案：前端分别请求列表与状态后拼接。未采用原因：增加前端复杂度与失败路径。

### 4) UI 风格使用 SCSS 主题化，不引入游戏引擎

- 决策：以 CSS/SCSS 实现偏游戏化视觉（配色、边框、动效），组件结构保持常规 React。
- 原因：满足“偏游戏向”同时保持低复杂度与高交付速度。
- 备选方案：Canvas/WebGL 引擎方案。未采用原因：超出初期范围且维护成本高。

### 5) 质量与规范默认纳入脚手架

- 决策：初始化即接入 ESLint + Prettier，并提供统一 npm scripts。
- 原因：避免后置治理成本，确保多人协作一致。
- 备选方案：后续再补。未采用原因：容易积累风格债务与低质量基线。

## Risks / Trade-offs

- [OpenCode 本地服务不可达或端口不一致] → 通过环境变量配置 base URL，后端返回可诊断错误码与错误信息。
- [Session 状态接口与列表数据更新时序不一致] → 以后端聚合时的快照语义为准，前端展示“最后刷新时间”。
- [偏游戏化样式过重影响可读性] → 先定义轻量主题 token，优先保障信息密度和可读性。
- [初期 schema 设计过简导致后续扩展成本] → 在响应中预留可扩展字段（如 summary、directory、version）。

## Migration Plan

1. 初始化 workspace 与前后端基础目录。
2. 建立 Koa API 路由与 OpenCode 客户端封装。
3. 建立 React 首页会话列表页面并接入后端 API。
4. 接入 SCSS 主题和基础组件样式。
5. 配置 ESLint/Prettier 与统一脚本，完成本地联调。

回滚策略：

- 若接入 OpenCode 失败，保留工程骨架并降级为静态占位数据模式，确保前后端构建链路可用。
- 若样式策略影响可用性，可回滚至基础样式主题文件，不影响数据链路。
